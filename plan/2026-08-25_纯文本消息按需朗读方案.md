# [已完成] 纯文本消息按需朗读方案

> **状态**：已完成 (Completed)
> **创建时间**：2026-08-25
> **完成时间**：2026-08-25
> **适用范围**：微光聊天页的纯文本 AI 回复
> **前置决策**：不自动朗读。只有用户点击某条 AI 消息旁的“播放”按钮时，才使用当前绑定的百炼克隆音色合成并播放该条文本。

## 1. 目标

为纯文本聊天中的每条 AI 消息提供独立的按需朗读能力：

- 点击“播放”才开始 TTS；
- 使用当前用户已绑定的 `voice_id`，没有克隆音色时回退到系统默认音色；
- 点击播放时不改变左侧光球状态，不进入“正在聆听/正在想想/回应中”；
- 同一时刻只播放一条消息；
- 再次点击当前消息可停止；点击另一条消息可停止旧播放并切换；
- 合成或播放失败时，仅在该消息旁显示错误，不影响文本对话。

## 2. 当前问题

当前纯文本聊天走：

```text
POST /api/chat/stream
→ 文本增量
→ 页面显示
```

该链路明确不调用 TTS，因此 AI 纯文本消息没有 `audioUrl`，页面不会显示播放按钮。语音输入轮次才走 `/api/chat-and-tts/stream` 并生成语音。

## 3. 交互设计

```text
AI 文本消息
  ├─ ▶ 播放
  ├─ 生成中（按钮禁用 + 简短 loading）
  ├─ ■ 停止
  └─ 朗读失败（轻量错误提示，可重试）
```

规则：

1. 仅 AI 消息展示朗读按钮；欢迎语是否展示由产品决定，首期可展示。
2. 用户点击前不请求 TTS，不产生额外费用。
3. 同一消息的临时音频 URL 可在短期内复用；过期后重新请求。
4. 纯文本输入和正在朗读可并存，但新发文本不会自动停止朗读；用户手动点击停止或切换消息时才停止。
5. 左侧光球保持 idle，不将手动朗读误表现为实时语音对话。

## 4. 后端接口

推荐新增单独的按需朗读接口：

```http
POST /api/messages/tts
X-Weiguang-User-ID: <local-user-id>
Content-Type: application/json
```

请求：

```json
{
  "text": "需要朗读的 AI 回复",
  "format": "wav",
  "sample_rate": 24000
}
```

响应：

```json
{
  "audio_url": "<short-lived-url>",
  "request_id": "...",
  "voice_id": "当前实际使用的音色",
  "expires_at": "..."
}
```

服务端处理顺序：

1. 校验文本长度，例如不超过 2,000 字符；
2. 根据 `X-Weiguang-User-ID` 读取 PostgreSQL `voice_clones` 的最新激活记录；
3. 有克隆音色则使用该 `voice_id`，否则使用 `QWEN_TTS_VOICE`；
4. 调用现有 `BailianTTSProvider.synthesize()`；
5. 返回临时音频 URL，禁止将 Qwen API Key 和 OSS 长期凭据下发浏览器；
6. 记录 request_id、延迟、字符数和错误码，便于后续配额/成本审计。

首期不需要重新调用 LLM，也不需要修改 `/api/chat/stream`。

## 5. 前端改造点

### 5.1 数据状态

每条 AI 消息增加：

```ts
audioUrl?: string
audioLoading?: boolean
audioPlaying?: boolean
audioError?: string
audioExpiresAt?: string
```

这些字段只描述手动朗读状态，与语音对话状态机隔离。

### 5.2 播放器

- 使用 `HTMLAudioElement` 播放 API 返回的完整音频 URL；
- 维护单一 `activeAudio` 和 `audioRequestId`；
- 请求返回后再次检查 requestId，防止旧请求覆盖新播放；
- 切换消息或停止时暂停播放器并清除当前状态；
- 不调用 `startRecognition()`、`setState("speaking")` 或语音回声门控。

### 5.3 历史消息

历史记录只保存文本内容；音频 URL 是临时资源，不持久化。

刷新页面后用户再次点击“播放”时重新调用 `/api/messages/tts`。这样避免在 localStorage 或 PostgreSQL 存储失效签名 URL。

## 6. 安全与限制

- 朗读接口必须从用户绑定记录选择 voice，不能信任浏览器传来的任意 `voice_id`；
- 限制单条文本长度、每分钟朗读次数和并发数；
- 临时音频 URL 设置合理有效期；
- 不记录完整文本或签名 URL到普通日志；
- 若用户未绑定克隆音色，明确使用系统默认音色，不报错；
- TTS 失败时不能影响文本消息已完成状态。

## 7. 验收标准

1. 纯文本 AI 消息显示“播放”按钮。
2. 点击后只产生一次 TTS 请求并开始播放。
3. 再次点击可停止当前播放。
4. 点击另一条消息可停止旧音频并播放新音频。
5. 当前绑定克隆音色可被实际使用；未绑定时系统音色可回退。
6. 播放时左侧光球仍保持 idle，文本聊天不变成语音会话。
7. 刷新后历史文本仍可重新点击朗读。
8. TTS 失败可见错误提示，文本聊天仍可继续。
9. 前端 build、后端接口 smoke、Chrome 手动播放均通过。

## 8. 实施步骤

1. 后端新增 `/api/messages/tts`，复用 `VoiceCloneStore` 和 `BailianTTSProvider`。
2. 前端 API 层新增 `synthesizeMessage()`。
3. ChatView 在 AI 气泡旁渲染播放/停止/错误状态。
4. 将手动播放器与实时语音播放器完全隔离。
5. 验证系统音色、克隆音色、停止/切换、URL 过期和刷新重试场景。

## 9. 未决事项

- 首期使用完整音频 URL，降低复杂度；若用户希望“点击后立即流式朗读”，后续可改用单独的 `/api/messages/tts/stream`。
- 是否把朗读计入用户配额和账单，待用量模型确定后决定。
- 是否允许用户选择“文本回复自动朗读”，不在本方案范围内。
