# [未完成] 链动小铺套餐兑换码售卖接入方案

> **状态**：未完成 (Pending)
> **创建时间**：2026-08-29
> **最近更新**：2026-08-31
> **适用范围**：微光 Plus / Pro 的外部售卖与兑换，不替代微光官方支付主链路
> **结论**：链动小铺首期只作为“卡密自动交付的外部销售渠道”；微光以自身数据库中的一次性兑换码和订阅记录作为唯一权益依据

## 1. 来源与核验边界

本方案读取的《链动小铺平台商家开店指引（新版）》说明：商家可注册开店、配置支付宝/微信/自配收款渠道、发布虚拟商品，并在商品下按“一行一个”上传卡密后由系统自动发货。该文档还宣称支付宝直清、微信支付和自配支付渠道的费率与结算规则。

已确认的文档能力仅限于：

- 虚拟商品与卡密库存；
- 商家订单与售后页面；
- 商家自行配置的收款渠道说明。

尚未获得或核验的内容：

- 链动小铺订单创建、查询、支付成功通知或退款 API；
- 回调验签规则、事件唯一 ID、重放防护和公网回调注册方式；
- 沙箱、测试商户、订单状态机和自动发货 API；
- 实际签约费率、结算时间、可售行业、退款规则和平台服务协议。

链动小铺公开站点的技术资料目前被验证页拦截，不能绕过该验证或把商家指引中的产品说明当作 API 合同。因此首期不做“支付成功回调 → 自动开通微光套餐”。

## 2. 与当前套餐体系的关系

当前微光已具备：

- 数据库存储的 `user_subscriptions`、`usage_events` 与 `/api/billing/summary`；
- `/pricing` 的免费体验、Plus 59 元/月、Pro 129 元/月展示；
- PostgreSQL 作为账户、套餐与用量的唯一权威来源；
- 浏览器转写 + 百炼 LLM/TTS 的当前业务链路。

当前微光未具备：

- 支付订单、支付回调、退款、对账或自动续费；
- 兑换码、发码批次、兑换接口和订阅授权流水；
- 已验证的链动小铺 API 或回调。

因此通道职责必须拆开：

```text
链动小铺
  └─ 售卖“微光套餐兑换码”并自动发出卡密

微光
  └─ 登录用户兑换卡密，原子更新自己的订阅权益与审计记录
```

微光不信任“用户截图”“前端传来的支付成功”或外部订单号；只有数据库中预生成、未撤销、未兑换的兑换码能发放权益。

## 4. 目标用户流程

```text
用户在微光 /pricing 查看套餐
  → 进入微光 /purchase/{plus|pro} 独立购买页
  → 点击“打开链动小铺购买”（外部商品链接）
  → 链动小铺支付并自动交付兑换码
  → 用户返回微光并登录
  → 输入兑换码
  → 微光服务端校验哈希、有效期、状态和套餐规则
  → 单个数据库事务：标记已兑换 + 创建订阅授权 + 更新 user_subscriptions
  → 返回当前套餐与到期日
```

购买与兑换入口放在：

1. `/pricing` 的 Plus / Pro “购买或兑换”按钮；
2. `/purchase/{planCode}` 的独立购买、返回和兑换页；
3. 个人中心“当前套餐”卡片内的“兑换权益码”按钮。

不在聊天输入框、声音设置或弹窗式广告中放置购买入口。

## 5. 兑换码与订阅规则

### 5.1 兑换码安全

- 使用密码学安全随机数生成至少 128 bit 熵的兑换码；
- 数据库只保存 `SHA-256(code)`，绝不保存可再次导出的原文；
- 原文只在生成批次时输出一次，随后由运营人员上传到链动小铺卡密库存；
- 单码只能兑换一次；卡密按批次设置固定到期日（建议预留至少 180 天），并在链动小铺商品页明确展示具体兑换截止日期；
- 微光无法在没有订单 API 的情况下获知每个卡密的实际售出时间，因此不得宣称“购买后 30 天内兑换”并据此自动计算卡密有效期；套餐权益仍从成功兑换时起计算 30 天；
- 兑换成功后立即绑定当前登录用户，不允许转移；
- 对 `/api/billing/redeem` 按用户、IP 和兑换码摘要限流；失败响应统一为“兑换码无效或不可用”，不泄漏码是否存在；
- 原始兑换码、链动小铺订单截图、支付凭据和完整外部订单号不写普通日志。

### 5.2 首期权益规则

- 免费用户兑换 Plus 或 Pro 码：立即切换到相应套餐，自兑换时间起 30 天；
- 同套餐有效期内兑换：在当前到期日后顺延 30 天；
- Pro 用户兑换 Plus 码：拒绝且不消耗兑换码，提示联系人工处理；
- Plus 用户兑换 Pro 码：首期不支持自动升档，拒绝且不消耗兑换码，提示联系人工处理；
- 已撤销、过期、已兑换或批次冻结的码：拒绝且不消耗；
- 退款只允许处理未兑换的码；已兑换权益的退款、降档与剩余额度回收由人工审核，不自动回滚。

首期故意不做跨套餐折算，避免支付渠道尚未验收时出现错误折价、重复发放或账务争议。

## 6. 数据模型与迁移边界

新增的业务数据全部写入 PostgreSQL，不使用 `localStorage`、浏览器存储或前端配置作为权威来源。

```text
redemption_batches
  id, channel, product_code, created_by, quantity,
  status, created_at, expires_at, uploaded_at

redemption_codes
  id, batch_id, code_hash UNIQUE, product_code,
  status, expires_at, redeemed_by_user_id, redeemed_at,
  revoked_at, created_at

subscription_grants
  id, redemption_code_id UNIQUE, user_id, plan_code,
  period_start, period_end, source_channel, created_at
```

当前项目的 FastAPI 迁移器只扫描 `backend/migrations/`，但最新 `AGENTS.md` 强制要求新增数据库迁移位于 `internal/auth/migrations/`。开始编码前必须先统一迁移机制：要么让当前服务安全执行该强制目录中的迁移，要么由项目维护者明确修订规范；禁止在两个目录各写一份迁移。

## 7. API 与事务

对用户只开放一个兑换接口：

```text
POST /api/billing/redeem
{
  "code": "用户输入的一次性兑换码"
}
```

服务端事务顺序：

1. 获取当前 HttpOnly 会话对应的用户；
2. 对输入码规范化并计算哈希；
3. `SELECT redemption_codes ... FOR UPDATE`；
4. 校验状态、有效期、套餐兼容性与限流；
5. 标记兑换码为 `redeemed`；
6. 写入唯一 `subscription_grants`；
7. 更新 `user_subscriptions` 的 `plan_code`、周期与状态；
8. 提交并返回新的 `/api/billing/summary`。

任何一步失败都回滚；`redemption_code_id UNIQUE` 与 `code_hash UNIQUE` 共同防止并发重复兑换。

## 9. 运营发码流程

1. 在受限服务端环境创建 Plus / Pro 兑换码批次；
2. 仅将该批次的原始码导出一次，上传到对应链动小铺卡密商品；
3. 记录批次编号、商品编号、码数量、上传人、上传时间和固定兑换截止日期；
4. 每日比对链动小铺已售数量与微光已兑换数量；
5. 发现卡密库存不足、重复发码、退款或异常兑换时，立即冻结该批次；
6. 过期或未售码由微光后台撤销后，不再复用。

链动小铺后台的订单状态只用于人工运营对账，不能自动修改微光订阅，直到取得并验证其官方 API/回调能力。

## 10. 官方支付与链动小铺的优先级

| 场景 | 推荐通道 | 权益发放方式 |
|---|---|---|
| 首期外部售卖验证 | 链动小铺卡密商品 | 微光兑换码 |
| 微光站内电脑支付 | 支付宝电脑网站支付 / 微信 Native | 官方异步通知验签后原子发放 |
| 手机浏览器支付 | 支付宝 WAP / 微信 H5 | 官方异步通知验签后原子发放 |
| 自动续费 | 暂不开放 | — |

链动小铺不替代已归档的微信/支付宝直连方案，而是让微光在官方商户支付资质与公网回调尚未完备时，先验证用户是否愿意购买套餐。

## 11. 链动小铺 API 的后续准入门槛

只有取得并核验以下官方资料后，才允许把链动小铺升级为自动履约通道：

1. 商家 API 文档、订单查询和支付成功事件；
2. 回调 URL 配置方式、签名算法、时间戳与重放防护；
3. 外部事件唯一 ID、订单状态机、退款事件和查单接口；
4. 测试环境或真实小额测试订单；
5. 平台允许售卖 AI 服务/订阅权益的书面确认；
6. 实际签约费率、结算周期、退款和争议处理规则。

达到门槛后，新增 `LdxpPaymentProvider` 只能作为现有支付通道的一个实现；它必须走与微信/支付宝相同的订单、验签、幂等和履约机制，不能直接更新订阅。

## 13. 当前结论

可以接入，但首期正确的接法是：

```text
链动小铺卖卡密 → 用户得到一次性微光兑换码 → 用户登录微光兑换 → 微光数据库发放套餐
```

不应采用：

```text
用户支付成功页跳回微光 → 前端直接把用户升级为 Plus / Pro
```

原因是后者没有可核验的支付回调、验签和幂等证据，且会让外部平台越过微光自己的权益账本。
