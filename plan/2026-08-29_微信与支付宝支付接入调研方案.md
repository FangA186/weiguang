> **状态**：未完成 (Pending)

> **2026-09-01 决策**：暂缓实施。首期继续使用已完成真实闭环验收的链动小铺支付与卡密交付，不重复建设微信/支付宝直连。

## 1. 调研结论

微光当前是浏览器 Web 产品，首期推荐按以下顺序接入：

1. **桌面 Web**：微信 Native 扫码支付 + 支付宝电脑网站支付；
2. **手机普通浏览器**：微信 H5 支付 + 支付宝手机网站支付（WAP）；
3. **微信内网页**：仅在后续具备已认证公众号和 OpenID 体系后增加 JSAPI 支付；
4. **首期不做自动续费**：Plus / Pro 先按“用户主动购买一个月”实现，支付成功后发放一个自然月或固定 30 天权益；
5. **首个联调通道优先支付宝沙箱**，再接微信 Native 正式小额支付。支付宝提供沙箱调试能力；微信基础支付联调需要真实商户参数和公网回调环境。

这套顺序最符合当前约 50 名邀请用户、59/129 元月套餐和 FastAPI 单体架构，不需要新增支付微服务，也不会把通道逻辑写进套餐业务。

## 2. 当前项目基础

已经具备：

- PostgreSQL 用户与 HttpOnly 会话；
- `user_subscriptions`：用户当前套餐、状态和周期；
- `usage_events`：AI 回复、TTS、多模态和音色用量；
- `/pricing` 套餐页：免费、Plus 59 元/月、Pro 129 元/月；
- `/api/billing/summary`：个人中心套餐和用量汇总；
- FastAPI + `httpx`：适合封装支付通道 HTTP 调用。

尚未具备：

- 商户订单、支付流水、回调事件、退款单和对账差异表；
- 微信/支付宝商户凭据与签名验签组件；
- Checkout、订单查询、关单、退款、回调 API；
- 套餐支付后的原子履约；
- 公开 HTTPS 域名和公网回调地址的验收证据。

## 3. 支付场景选择

| 使用场景 | 微信支付 | 支付宝 | 首期建议 |
|---|---|---|---|
| 桌面浏览器 | Native，下单返回 `code_url`，前端生成二维码 | `alipay.trade.page.pay`，跳转支付宝收银台 | 首发支持 |
| 手机普通浏览器 | H5，下单返回 `h5_url` | `alipay.trade.wap.pay` | 第二批支持 |
| 微信内置浏览器 | JSAPI，需要公众号/小程序 AppID、OpenID | 不作为主路径 | 后续单独立项 |
| 原生 App | APP 支付 | APP 支付 | 当前不做 |
| 自动续费 | 委托代扣/免密服务，需额外审核和用户授权 | 周期扣款产品，需另行签约评估 | 首期不做 |

### 3.1 微信 Native

服务端调用：

```text
POST https://api.mch.weixin.qq.com/v3/pay/transactions/native
```

返回 `code_url`，有效期通常与订单支付时效一致，官方文档说明二维码链接最长有效 2 小时。前端只负责把 `code_url` 渲染成二维码，并轮询微光自己的订单状态，不直接查询微信接口。

### 3.2 微信 H5

服务端调用：

```text
POST https://api.mch.weixin.qq.com/v3/pay/transactions/h5
```

返回 `h5_url`，前端在已配置的支付域名中跳转。该能力不能在 `localhost` 正式使用：需商户号开通 H5 支付、已备案且公网可访问的经营/支付域名，并在商户平台完成域名配置。

### 3.3 支付宝电脑网站支付

后端通过官方 Python SDK 调用：

```text
alipay.trade.page.pay
```

服务端生成支付页面跳转内容或 URL，浏览器跳转支付宝收银台。`return_url` 只负责用户体验，不能作为支付成功依据。

### 3.4 支付宝手机网站支付

调用：

```text
alipay.trade.wap.pay
```

用户在手机网页/支付宝 App 收银台完成支付后回到微光。支付结果仍以支付宝异步通知或主动查询为准。

## 4. 商户与上线准备

### 4.1 微信支付

必须准备：

- 微信支付普通商户号；
- 与商户号绑定的公众号、小程序或移动应用 AppID；
- 商户 API 证书序列号及私钥；
- API v3 密钥；
- 微信支付公钥 ID 与公钥文件（官方当前推荐公钥验签模式）；
- 公网 HTTPS `notify_url`；
- H5 支付权限和已配置支付域名（若开放手机浏览器支付）；
- 真实的商品/服务介绍、价格区间、隐私政策、用户协议和退款规则。

微信 H5 权限审核与域名配置可能分别需要数个工作日，实际以商户平台审核为准。

### 4.2 支付宝

必须准备：

- 支付宝开放平台企业应用；
- 开通电脑网站支付、手机网站支付产品；
- `app_id`；
- 应用 RSA2 私钥和支付宝公钥；
- 公网 HTTPS `notify_url` 与支付完成 `return_url`；
- 应用审核通过并上线；
- 沙箱应用、沙箱账号和沙箱网关用于首轮联调。

支付通道费率、结算周期、退款手续费和行业限制以商户实际签约页面为准，禁止在代码或报价方案中写死通用费率。

## 5. 推荐系统架构

```text
Vue /pricing
  → POST /api/billing/checkout
      → 服务端读取套餐和价格
      → PostgreSQL 创建 payment_order
      → PaymentProvider.create_payment()
      → 返回二维码内容或收银台 URL

微信 / 支付宝
  → POST /api/billing/webhooks/{provider}
      → 原始请求验签 / 微信通知解密
      → 校验商户、应用、订单号、金额、币种
      → payment_events 幂等落库
      → payment_orders 原子改为 PAID
      → user_subscriptions 原子发放权益
      → 快速响应通道成功

浏览器
  → GET /api/billing/orders/{order_no}
      → 只读取微光数据库订单状态
```

支付回调链路不能相信前端传入的“支付成功”，也不能只相信同步跳转。微信和支付宝官方都要求回调验签，并建议结合查单接口处理通知丢失或延迟。

## 6. Provider 边界

统一接口建议：

```python
class PaymentProvider(Protocol):
    async def create_payment(self, order, client_context) -> CheckoutResult: ...
    async def query_payment(self, order) -> ProviderPayment: ...
    async def close_payment(self, order) -> None: ...
    async def create_refund(self, order, refund) -> ProviderRefund: ...
    async def query_refund(self, refund) -> ProviderRefund: ...
    def verify_and_parse_notification(self, headers, body) -> PaymentNotification: ...
```

建议目录：

```text
backend/payments/
├── base.py
├── wechat.py
├── alipay.py
└── service.py
```

- 套餐、金额、权益只由 `service.py` 和数据库决定；
- Provider 只负责通道协议，不直接修改订阅；
- 微信与支付宝的订单号、状态和错误码统一转换成内部模型。

## 7. 数据模型

### 7.1 `payment_orders`

```text
id                  BIGSERIAL
order_no            TEXT UNIQUE             # 微光订单号
user_id             TEXT
product_type        TEXT                     # subscription / addon
product_code        TEXT                     # plus_monthly / pro_monthly
amount_fen          INTEGER                  # 人民币分，禁止浮点
currency            TEXT DEFAULT CNY
provider            TEXT                     # wechat / alipay
status              TEXT                     # CREATED/PENDING/PAID/FULFILLED/CLOSED/FAILED
provider_order_id   TEXT
provider_trade_state TEXT
expires_at          TIMESTAMPTZ
paid_at             TIMESTAMPTZ
fulfilled_at        TIMESTAMPTZ
created_at/updated_at
```

### 7.2 `payment_events`

```text
id, provider, provider_event_id, order_no, event_type,
signature_valid, payload_digest, received_at, processed_at,
UNIQUE(provider, provider_event_id)
```

不保存完整敏感支付报文；保留脱敏后的必要审计字段和 SHA-256 摘要。

### 7.3 `refund_orders`

```text
id, refund_no UNIQUE, order_id, user_id, amount_fen,
reason, provider_refund_id, status, requested_at, succeeded_at
```

### 7.4 `subscription_grants`

```text
id, order_id UNIQUE, user_id, plan_code,
period_start, period_end, status, created_at
```

`order_id UNIQUE` 是防止重复回调重复发放套餐的最后数据库护栏。

## 8. 内部状态与事务

```text
CREATED → PENDING → PAID → FULFILLED
                 ↘ CLOSED
                 ↘ FAILED

FULFILLED → REFUND_PENDING → PARTIALLY_REFUNDED / REFUNDED / REFUND_FAILED
```

回调处理必须在数据库事务中执行：

1. 插入 `payment_events`；重复事件直接返回成功；
2. `SELECT payment_orders ... FOR UPDATE`；
3. 校验订单状态、用户、金额和币种；
4. 更新订单为 `PAID`；
5. 插入唯一 `subscription_grants`；
6. 更新 `user_subscriptions`；
7. 提交事务。

同一个 `order_no`、同一个回调或同一个退款单重复执行，最终只能产生一次权益变化。

`POST /api/billing/checkout` 请求只允许提交：

```json
{

  "provider": "wechat",

}
```

金额、套餐权益、促销价和有效期必须由服务器读取，不能接受前端金额。

## 10. 通道安全细节

### 10.1 微信 API v3

- 请求使用商户 API 证书私钥进行 SHA256-RSA2048 签名；
- 微信响应和回调使用微信支付公钥/平台证书验签；
- 回调资源使用 API v3 密钥执行 AES-256-GCM 解密；
- 回调验签串必须使用原始请求体，JSON 重新序列化会导致验签失败；
- 需处理微信签名探测流量，验签失败绝不能更新订单；
- 微信要求回调在 5 秒内响应，先完成验签和可靠落库，再异步做非关键业务；
- 微信可能重复通知，必须持续幂等并返回 `200/204`。

微信官方当前列出的服务端 SDK 主要是 Java/PHP/Go，没有官方 Python SDK。当前 FastAPI 项目推荐用 `httpx + cryptography` 实现一个小型 API v3 Adapter，并用微信官方签名验签工具和样例做固定向量测试；不直接采用来源不明的社区 SDK。

### 10.2 支付宝 RSA2

- 使用支付宝开放平台官方 Python SDK；
- 应用私钥仅用于服务端请求签名；支付宝公钥用于响应和通知验签；
- 异步通知剔除 `sign`、`sign_type` 后按官方规则验签；
- 验签后仍需核对 `app_id`、`out_trade_no`、`total_amount` 和收款方；
- 仅 `TRADE_SUCCESS` / `TRADE_FINISHED` 可进入支付成功处理；
- `return_url` 参数不能发放套餐，只显示“正在确认支付”并查微光订单状态。

## 11. 前端交互

### 桌面端

- Plus / Pro 卡片从“即将开放”改为“立即开通”；
- Checkout 弹窗选择微信或支付宝；
- 微信展示二维码、订单金额、套餐名和有效期倒计时；
- 支付宝跳转电脑网站收银台；
- 页面每 2 秒查询微光订单状态，成功后停止轮询并刷新个人中心；
- 页面关闭/超时后由后端查单与关单任务收尾。

### 手机端

- 支付宝直接跳转 WAP 收银台；
- 微信普通浏览器跳转 `h5_url`；
- 微信内浏览器在未接 JSAPI 前明确提示“请在系统浏览器打开或使用支付宝”，不能伪装支付失败。

## 12. 自动续费边界

标准 Native/H5/Page/WAP 支付都是用户主动支付，不能直接实现自动续费。

微信自动续费需要委托代扣权限、模板、显著授权协议、扣费前通知和解约入口；部分新能力仍处于灰度或需运营评估。支付宝周期扣款也需要单独产品签约和用户授权。

因此首期定义为：

```text
Plus / Pro = 单次购买一个月权益
到期前 7/3/1 天提醒用户主动续费
不默认勾选、不静默扣款、不宣传“自动续费”
```

完成两个月真实运营、退款和对账后，再单独调研委托代扣。

## 13. 对账、退款与补偿

- 每日下载微信/支付宝账单，与 `payment_orders` 对账；
- 生成缺单、金额不一致、状态不一致列表，禁止自动忽略；
- 退款前先查支付订单；退款接口返回“受理”不等于退款完成；
- 退款最终状态以退款回调或退款查询为准；
- 支付成功但履约失败时进入 `PAID_UNFULFILLED` 告警队列，由幂等补偿任务重新发放；
- 套餐退款后的额度回收规则必须先由产品确认，已消耗额度不得简单恢复成未支付状态。

## 16. 验收门槛

- 金额只能来自服务端，单位统一为“分”；
- 重复通知 100 次仍只发放一次权益；
- 伪造签名、错金额、错 AppID/MchID/Seller 必须被拒绝；
- 支付成功回调丢失时，主动查单能补齐；
- 支付成功但数据库事务失败时，补偿任务能恢复；
- 全额退款、部分退款、退款处理中、退款失败均有明确状态；
- 日对账能发现通道有单/本地无单及本地已付/通道未付；
- 私钥、API v3 密钥和支付通知敏感字段不进入代码与日志；
- 至少完成支付宝沙箱全流程、微信真实小额支付与退款；
- 未完成以上验收前，Plus/Pro 继续显示“即将开放”。
