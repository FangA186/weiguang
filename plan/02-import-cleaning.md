# 阶段 1：聊天记录导入与数据清洗

## 1. 业务目标

用户上传聊天记录后，系统自动删除不需要的数据，保留文字和图片，并提供可读、可核对的清洗报告。

前端示例：

```text
原始消息：12,500 条
保留消息：10,200 条
保留图片：320 张
删除视频：108 个
删除音频：21 个
删除其他附件：42 个
警告：3 张图片文件缺失
```

## 2. 清洗规则

### 保留

- 消息正文；
- 发送人 ID 和显示名；
- 原始时间和标准化时间；
- 回复关系和必要元数据；
- JPEG、PNG、WebP、GIF 图片；
- 图片 OCR 和视觉描述。

### 删除

- MP4、MOV、AVI、WebM 等视频；
- 音频文件；
- PDF、Office、压缩包等普通附件；
- 未知媒体；
- 视频 URL；
- 视频缩略图。

如果一条消息只有视频且没有正文，则只增加清洗统计，不创建可检索消息。若消息同时包含文字和视频，则保留文字、删除视频，并在 `metadata.removed_attachments` 记录数量。

## 3. 消息规范化

- 时间统一为 `TIMESTAMPTZ`；
- 保留原始时区信息；
- 统一换行和 Unicode；
- 清除零宽字符和控制字符；
- 不修改用户原始语义；
- 根据 `external_id` 和内容哈希去重；
- 空文本且无有效图片的消息不入库。

消息哈希建议包含：

```text
collection_id + sender_id + occurred_at + normalized_content
```

## 4. 图片流水线

```text
读取图片
  ↓
文件头与真实 MIME 校验
  ↓
像素和文件大小限制
  ↓
SHA-256 去重
  ↓
清除 EXIF
  ↓
生成 WebP/JPEG 缩略图
  ↓
OCR
  ↓
视觉描述
  ↓
保存 asset 元数据
```

原图存放在私有目录：

```text
MEMORY_STORAGE_DIR/
└── user-id/
    └── collection-id/
        ├── original/
        └── thumbnails/
```

数据库不存储物理绝对路径，只保存相对于 `MEMORY_STORAGE_DIR` 的 storage key。

## 5. 数据表

### `memory_imports`

保存原始文件名、格式、哈希、大小、状态、进度、警告、错误和清洗统计。

### `memory_messages`

保存清洗后的正文、发送人、时间、重要度、置信度、搜索字段和元数据。

### `memory_assets`

保存图片哈希、MIME、storage key、缩略图、尺寸、OCR、描述和分析状态。

## 6. 图片分析失败策略

- OCR 失败：保留原图和缩略图，视觉描述仍可继续；
- 视觉描述失败：保留 OCR；
- 两者都失败：图片仍可预览，collection 进入 `partial_ready`；
- 重试只处理失败图片，不重复处理成功图片；
- OCR/描述结果不能直接升级为高置信事实，必须保留图片来源。

## 7. API 输出

```json
{
  "status": "partial_ready",
  "input_messages": 12500,
  "kept_messages": 10200,
  "kept_images": 320,
  "dropped_videos": 108,
  "dropped_audio": 21,
  "dropped_unknown": 42,
  "warnings": [
    "3 条消息引用了不存在的图片"
  ]
}
```

## 8. 验收标准

- 视频、音频和未知附件不落库、不落磁盘。
- 图片真实类型校验、去重和 EXIF 清理有效。
- 图片缺失不影响消息正文入库。
- 重复导入不会重复插入相同消息。
- 用户可以查看清洗报告和图片缩略图。
- 删除 collection 后图片和数据库记录同步删除。

## 9. 风险与处理

| 风险 | 处理 |
|---|---|
| OCR 误识别 | 标记来源与置信度，不直接当作事实 |
| 图片分析耗时 | 异步处理并允许 partial_ready |
| 大量重复图片 | SHA-256 去重 |
| 文件伪装 | 文件头和解码器双重验证 |
| 用户希望保留视频内容 | 第一版只保留伴随文字，后续可增加视频转写转换器 |
