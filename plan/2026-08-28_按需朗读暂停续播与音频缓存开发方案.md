> **状态**：未完成（代码与服务验收通过，待 Chrome 交互复测）
> **创建时间**：2026-08-28
> **完成时间**：待 Chrome 交互验收通过后填写

## 一、背景与问题

聊天页 AI 消息的按需朗读目前存在两类体验问题：

1. 播放中再次点击会执行 `pause()`、将 `currentTime` 重置为 `0` 并销毁播放器，因此下一次只能从头播放，实际行为是“停止”而不是“暂停”。
2. 百炼非流式 TTS 返回临时 `audio_url`。页面虽然在消息对象中暂存该 URL，但没有把音频内容缓存为浏览器本地 Blob；重新创建播放器时仍可能再次访问远端媒体 URL，页面刷新后还会重新调用 `/api/messages/tts`。

## 二、目标

- 同一条消息播放中再次点击时暂停并保留进度；再次点击从暂停位置继续播放。
- 同一条历史消息首次合成并下载后，将音频持久化到浏览器缓存；刷新页面后继续复用，不重新调用 TTS 或下载远端 URL。
- 切换到另一条消息、进入实时语音或开始新一轮播放时，停止旧音频且不串音。
- 音频真正播放结束后，下次从头播放，但继续复用已缓存音频。
- 组件卸载时释放所有 Blob URL，避免内存泄漏。

## 三、实现边界

### 3.1 最小状态

在 `frontend/src/views/ChatView.vue` 内复用现有 `Message`、`manualAudio` 和请求序号，增加：

- 当前手动播放器所属消息 ID；
- 当前页面会话的 `Map<messageId, blobUrl>`；
- 必要的暂停状态，或由 `manualAudio.paused && currentTime > 0` 直接判断。

### 3.2 播放流程

1. 当前消息正在播放：仅执行 `pause()`，保留 `currentTime` 和 `Audio` 实例。
2. 当前消息已暂停：复用同一个 `Audio` 实例并调用 `play()` 续播。
3. 当前消息已有内存 Blob URL：直接创建播放器，不调用 TTS、不重新下载远端媒体。
4. 内存未命中时，按“用户 ID + 稳定消息 ID + 文本 + 音色 +角色指令”生成缓存键并查询浏览器 Cache Storage；命中后从持久缓存恢复 Blob URL。
5. 持久缓存也未命中时，调用 `/api/messages/tts` 获取 `audio_url`，用 `fetch` 下载并校验响应，将音频写入 Cache Storage，再创建 Blob URL 播放。
6. 播放结束：将进度归零并保留内存及持久缓存。
7. 切换消息或进入其他音频模式：停止当前播放器，但保留缓存；新对话清除当前用户对应的持久缓存。

### 3.3 持久缓存边界

- 使用浏览器原生 Cache Storage 保存音频响应，不新增依赖、不引入 Service Worker 或后端音频表。
- 缓存键包含用户、消息正文和当前音色/角色指令摘要，避免不同用户或音色配置错误复用。
- 缓存最多保留 30 条音频，超过上限淘汰旧条目；浏览器仍可按自身存储策略回收。
- 页面刷新或普通路由切换只释放内存 Blob URL，不删除持久缓存；点击“新对话”时清理对应持久音频。

## 四、异常处理

- `audio_url` 请求非 2xx 时显示明确错误，不缓存错误响应。
- 响应 `Content-Type` 不是 `audio/*` 时拒绝播放，避免把 HTML/JSON 错误页交给浏览器媒体解码器。
- 合成或下载失败后清除该消息的失效 URL，使下一次点击可以重新尝试。
- 继续使用现有请求序号避免旧请求覆盖新播放状态。

## 五、验收标准

1. 首次点击某条 AI 消息：恰好一次 `/api/messages/tts` 和一次远端音频下载，随后开始播放。
2. 播放中点击暂停，等待后再次点击：从原时间点继续，不从头播放。
3. 同一条消息播放结束后再次点击：从头播放，不再请求 `/api/messages/tts`，也不再访问远端音频 URL。
4. 刷新 `/chat` 后再次播放同一条历史消息：直接命中浏览器持久缓存，不请求 `/api/messages/tts` 和远端 WAV。
5. 在两条消息之间切换：旧音频立即停止，新音频独占播放，无状态串联。
6. 新对话清理对应持久缓存；实时语音和组件卸载路径不残留手动播放器或 Blob URL。
7. `npm run build` 通过；Chrome Network 与 Application/Cache Storage 完成复测。
